# Decisions log

## 2026-10-12

- **Scaffold**: Next.js (App Router, TypeScript, `src/` dir) + Tailwind, deployable to Vercel Hobby for free. Chosen per `docs/PACKET.md` stack table.
- **Auth**: Supabase Auth with the Google provider via `@supabase/ssr` (browser client, server client, and session-refresh proxy). `redirectTo` is built from `window.location.origin` at click time (`src/components/GoogleSignInButton.tsx`), not a hardcoded URL, so the same code works on `localhost` and on the Vercel deploy domain.
- **Next.js 16 migration**: the framework renamed the `middleware.ts` convention to `proxy.ts` (exported function `proxy` instead of `middleware`). Migrated immediately to avoid building on a deprecated API.
- **Cache Components**: disabled `cacheComponents` in `next.config.ts`. Every route in this app reads the Supabase session via cookies, so nothing can be statically prerendered — leaving the experimental caching mode on only produced build errors for no benefit here.
- **.gitignore**: kept the blanket `.env*` ignore rule but added `!.env.example` so the variable-name template is the one `.env*` file tracked in git. `.env.local` (real Supabase URL/anon key, HMAC secret) stays untracked and local-only.
- **Known issue — Safari on localhost**: Google sign-in works end-to-end in Chrome (redirects through `/auth/callback` to `/app`, shows the first name). In Safari, `localhost` sign-in leaves the page blank after the Google redirect. Not yet root-caused; likely candidates are Safari's Intelligent Tracking Prevention blocking the Supabase auth cookie on `localhost`, or the OAuth popup/redirect flow behaving differently in Safari's dev-mode cookie jar.
- **Deploy 1**: live at **https://mi-total.vercel.app**. Confirmed Google sign-in works end-to-end there in both Safari and Chrome — the earlier blank-page issue is specific to Safari + `localhost` (cookie/ITP behavior), not a bug in the auth flow itself. No further action needed on the real domain; revisit only if it resurfaces for local dev testing in Safari.
- **Feature 2 — upload + validation**: shared `validateScreenshotFiles` (1–3 files, PNG/JPEG, ≤4 MB) runs both client-side and inside `POST /api/extract` (401 if no session, 400 with a clear message otherwise). Verified the shared validation logic against all required cases (0/1/3/4 files, PDF, 5 MB image) and the 401 boundary live; could not exercise the authenticated 400 cases end-to-end without a browser session.
- **Feature 3 — vision extraction + fallback**: split the extraction logic into a pure, dependency-injected `runExtraction`/`parseExtractionText` (`src/lib/extraction/core.ts`, no network, fully unit-testable with Vitest) from the real network call (`src/lib/extraction/gemini.ts`, Gemini `gemini-2.5-flash`, only imported by the route handler). `GEMINI_API_KEY` is empty in `.env.local` for now, so `/api/extract` always serves the labeled simulated fixture (3 fictional lenders) — this is automatic per the owner's instruction, not a bug. Malformed/unparseable LLM output clamps amounts to 0–1,000,000 then falls back to `{ error: "manual" }` rather than guessing. 9 Vitest cases cover: valid payload, out-of-range clamping, malformed JSON, missing required field, markdown-fenced JSON, no-key fallback, forced-simulated fallback, Gemini-throws fallback, and real-shaped success.
- **Testing approach for authenticated routes**: per the owner's instruction (exams, no browser testing), business logic that doesn't need a live session is covered with Vitest; the 401/unauthenticated boundary is checked live with curl; the authenticated 200/400 paths are exercised only through unit tests of the same code the route calls, not through a real authenticated HTTP round-trip (no browser session available to this agent).
- **Feature 4 — review table, peso math, incomplete notice**: pure functions in `src/lib/debtMath.ts` (`computeTotal`, `computeQuincenaDue`, `computeYearlyCost`, `isPictureIncomplete`), 8 Vitest cases across 3 fixed scenarios (complete picture matching the mockup's $8,450 total, one row missing CAT, one row missing date + list not confirmed). Rows persist to `localStorage` only (`src/lib/localDebtStorage.ts`, try/catch, SSR-safe `typeof window` guard) — confirmed via `grep` that the only `fetch` call anywhere in client code is the original screenshot upload; nothing about the edited rows ever reaches the server. `UploadForm` now reports its result to a new `DebtFlow` component instead of rendering it inline, since the editable table superseded Feature 3's read-only preview.
- **Lint rule exception**: `react-hooks/set-state-in-effect` flagged the one-time `localStorage` hydration-on-mount effect in `DebtFlow`. Kept the effect (reading `window.localStorage` during render would mismatch the server-rendered HTML) and added a scoped `eslint-disable` for that block instead of restructuring around the rule.

- **Feature 5 — comprehension check + signed token**: `src/lib/token.ts` has the HMAC-SHA256 signer (`userId|issuedAt|pictureComplete|comprehensionPass|loansCount`) and a `.strict()` Zod schema that only accepts `picture_complete`, `comprehension_pass`, `loans_count` — any extra field (e.g. an amount) is rejected outright, enforcing "never amounts" at the schema level, not just by convention. `POST /api/token` (401 if no session) inserts through the existing Supabase server client, so the real `tokens` RLS policies — not a service-role bypass — gate the write. UI: `ComprehensionStep` hides the total, asks "Sin ver arriba, ¿cuánto debes en total?", then reveals the same total card a second time before the "Entendido, sigo" button fires the token request; `comprehension_pass = |answer − total| ≤ 10%` is computed client-side and sent as a boolean only. The message after token issuance ("Listo. Ya viste tu panorama completo.") is identical whether the check passed or failed, per the never-judge rule. 7 Vitest cases cover signature determinism/sensitivity and schema accept/reject paths (including the amount-smuggling rejection).
- **Migration already applied**: the owner ran `supabase/migrations/001_tokens.sql` directly in Supabase before this feature was built — `tokens` and `token_aggregates()` already exist with RLS live.
- **RLS live-test attempted, skipped safely**: planned to verify "user B cannot read user A's tokens" against the real database using two throwaway accounts (via `supabase.auth.admin.createUser`), insert/select/cross-read/spoof-insert, then delete both accounts and the test row. Aborted before creating anything: `SUPABASE_SERVICE_ROLE_KEY` is empty in `.env.local`, and that key is required for both creating and later deleting the test accounts — proceeding without the ability to clean up would have left orphaned accounts in the real project. Confirmed instead by re-reading the applied policies (`auth.uid() = user_id` on both select and insert, no update/delete) against what the route sends. **If you want this exercised live, set `SUPABASE_SERVICE_ROLE_KEY` in `.env.local` and ask for it again** — the throwaway-account test script is easy to redo safely once cleanup is possible.
- **Feature 6 — funder view (`/fondo`)**: server component fetches `token_aggregates()` once via RPC (never a per-row `select` on `tokens` — confirmed by grep) and hands the aggregate to the client `FunderView`. Pure math in `src/lib/funderMath.ts` (`costPerComprehendedUser`, `usersFundable`, `requiredLevyRate`), 6 Vitest cases. Editable assumptions default to the packet's numbers (cost/gated user MX$200, levy pool MX$300M, lender revenue base MX$6.811B) plus a new "meta de usuarios a financiar" input (MX$1,000,000 default) that the prompt's levy-rate formula needs but never named as its own field — treated as the "N users" from `docs/PACKET.md`'s funder-math section. `sessions < 10` shows "Muestra insuficiente" in place of both percentages and the computed math/chart, since the real `tokens` table is empty right now and a 0-session rate would be meaningless. Bar chart (Recharts) compares users-fundable-with-the-pool vs. the target, single teal hue with direct value labels (no legend needed for one series, per the dataviz skill's guidance) — skipped the categorical-palette validator since there's no multi-hue identity encoding here, just one measure in one color.
